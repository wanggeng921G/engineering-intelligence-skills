# Routing and risk

Identify requested deliverable, affected domains, artifacts, and authorized actions. Advice does not authorize editing, deploying, ordering, flashing, or energizing.

| Trigger | Skill |
|---|---|
| External specifications, standards, changing facts | `ei-grounded-citations` |
| Trade-offs or conflicting evidence | `ei-evidence-map` |
| Checkable technical recommendation | `ei-doublecheck` |
| High-impact, disputed, or explicitly challenged fact | `ei-fact-check` |
| Implementation, bug fix, test plan | `ei-engineering-execution` |
| Circuit, power, PCB, sensor, EMC | `ei-electronics-review` |
| MCU, RTOS, driver, firmware | `ei-embedded-review` |
| App, API, data, service | `ei-software-review` |
| LLM, agent, RAG, evaluation | `ei-ai-system-review` |
| Component boundaries and interfaces | `ei-system-architecture-review` |
| Technical survey or vendor comparison | `ei-technical-research-review` |

Use the smallest relevant set. Routine work needs key fact and acceptance checks. Elevated risk (damage, security/privacy, compatibility, persistent data, money, uptime) needs exact versions/parts, a failure mode, and independent verification. Critical risk (injury, physical hazard, field recovery, regulated claims, irreversible production effect) needs controlled primary evidence, blocking unknowns, safe tests, and qualified review.

Mark unsupported claims unverified and name the needed document or test. Never report proposed checks as passed. Cite exact sections/pages for consequential parameters.
